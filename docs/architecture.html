Banking Operations Copilot

An internal Spring Boot application with two parts. A copilot answers branch-staff questions from approved synthetic documents with exact citations, or refuses when the documents don't cover the question. Service requests need a supervisor's approval before any simulated action runs. This page covers the architecture, data model, API contract, security rules, AI internals and the decisions behind them.

Overview

Two roles, one modular monolith, one database. AI is used to retrieve, validate, answer and draft. It never approves or executes anything.

Branch employee

  • Ask the copilot and read cited answers
  • Create, edit and submit their own drafts
  • See the status and history of their own requests

Supervisor

  • Everything an employee can do
  • Approve, reject with a reason, or edit and approve
  • Upload documents, read audit trails and AI cost, provision users

Hard guarantees

  • No execution without a supervisor's approval
  • Each approved request executes at most once
  • No answer without a verified citation

Key flows

Ask the copilot

The orchestrator runs typed agents in sequence, each with its own timeout. If any step fails or times out, the orchestrator stops and the request takes the fallback path. Every model call is metered under the same run ID.

  O->>O: screen question (injection, too vague) → refuse early

    KR->>H: search(query, k=5)

Request lifecycle

RequestStatus.canMoveTo() holds the only transition table, and ServiceRequest.moveTo() is the only way to change status. Any other move returns 409 Conflict.

stateDiagram-v2

Category payloads (JSONB, typed in Java)

@JsonTypeInfo(use = NAME, property = "category")
public sealed interface RequestPayload {
    record CardService(String customerReference, String cardLast4, CardIssue issueType,
                       String deliveryBranch, String notes) implements RequestPayload {}
    record DigitalBanking(…) implements RequestPayload {}
    record AccountService(…) implements RequestPayload {}
    record AdditionalDocumentation(…) implements RequestPayload {}
}

Drafts may be incomplete, so the records only carry size limits. The business rules live in CategoryValidator, which switches over the sealed type (the compiler checks every category is handled) and reads its limits from copilot.requests.*. Results are stored as ERROR or WARNING issues: errors block submit and approval, warnings are shown to the supervisor.

CategoryFieldsBusiness rules (CategoryValidator)
Card servicecustomerReference, cardLast4, issueType, deliveryBranch, notesLOST/STOLEN → WARNING to confirm the block; STOLEN without "police" in notes → WARNING
Digital bankingcustomerReference, channel, issueType, registeredMobile, notesMobile matches ^01[0125]\d{8}$; DEVICE_CHANGE on INTERNET_BANKING → ERROR
Account servicecustomerReference, accountLast4, accountType, serviceType, periodFrom?, periodTo?, notesSTATEMENT needs both dates (ERROR), end after start (ERROR), period over 12 months (WARNING); CHEQUE_BOOK on a non-CURRENT account → ERROR
Additional documentationcustomerReference, relatedReference?, requiredDocuments[], dueDate, notesAt least one document (ERROR); due date in the past (ERROR); more than 14 days away (WARNING)

An ERROR blocks submission and approval. A WARNING is shown to the supervisor, who may fix it through edit-and-approve.

Security model

Authorization is checked in three layers, and the database backs up the most important rules. Any single layer would block a direct API call on its own.

1 · Filter chain

URL rules in SecurityFilterChain: /api/approvals/**, /api/audit/**, /api/users/** and document writes require ROLE_SUPERVISOR. Everything else requires authentication.

2 · Method security

@PreAuthorize("hasRole('SUPERVISOR')") on approval, audit and provisioning services, with a role hierarchy SUPERVISOR > EMPLOYEE.

3 · Domain policy

RequestAccessPolicy handles ownership (404 for non-owners), owner-only edits and submits, and segregation of duties (no self-decision). Plain Java, unit-tested.

select c.id from DocumentChunk c
where c.document.status = ACTIVE and c.suspicious = false
order by cosine_distance(c.embedding, :query)
limit 20

-- keyword (native SQL; the query words are OR-ed so a passage needs only some of them)
with q as (select replace(plainto_tsquery('english', :text)::text, '&', '|')::tsquery as query)
select c.id from document_chunk c join document d on d.id = c.document_id cross join q
where d.status = 'ACTIVE' and not c.suspicious and c.content_tsv @@ q.query
order by ts_rank_cd(c.content_tsv, q.query) desc
limit 20

The two ranked lists are merged with Reciprocal Rank Fusion. RRF uses only rank positions, so cosine similarities and ts_rank_cd scores never need to be normalised against each other. The cosine similarity of each fused passage is then computed in Java from its stored embedding and used by the pre-check and as the citation score. Supervisors can inspect the semantic, keyword and fused ranks with GET /api/search?q=.

RRF(d) = Σr ∈ {semantic, keyword} 1 / (k + rankr(d)) · k = 60 · ties go to the better semantic rank

USER

Evidence gets short labels (E1…E5) rather than database IDs, which are easier for a model to copy exactly. Any <evidence> or <question> tags inside the question or a passage are stripped, so text can't break out of its block. The guard turns [E3] markers into the [1], [2] numbering the UI shows.

Before generation (PreCheck)

  • Refuse instructions aimed at the copilot inside the question, without searching
  • Refuse questions with fewer than two meaningful words
  • Refuse if no retrieved passage reaches similarity 0.35, without calling the model
  • Superseded, retired and suspicious chunks are excluded in the search queries

After generation (CitationGuard)

  • An answer with no [E…] marker is withheld
  • An answer citing any passage that was not retrieved is withheld entirely, not patched
  • A reply that isn't valid JSON is treated as a refusal
  • A failed model call becomes a refusal with a FAILED step (Phase 5 adds the fallback path)

Observability

Correlation

CorrelationIdFilter takes X-Request-Id (or generates a UUID), stores it in the MDC as runId and echoes it back. StepRunner copies it into each agent step. History rows, audit events and AI usage all carry it.

Logs

ECS JSON on stdout (logging.structured.format.console=ecs), with runId on every line; agent steps add agent, status and duration, and copilot runs add mode, refusal, citations, tokens and latency. Prompts and answers are never logged.

AI usage and cost

Every model call goes through ModelGateway, which reads ChatResponse.metadata.usage (estimating characters / 4 when the provider reports none) and returns it with the reply. RunRecorder writes one ai_usage row per call. Cost = prompt × input price + completion × output price, from LLM_INPUT_USD_PER_MILLION and LLM_OUTPUT_USD_PER_MILLION.

Decisions

Each decision records the choice, the alternatives considered and the reason.

ADR-01

Modular monolith

ChosenOne Spring Boot app with one top-level package per module.

OverMicroservices.

BecauseThe brief names it as the baseline, there's one database, and transactional approval-plus-execution is simpler in one process.

ADR-02

Flyway owns the schema, Hibernate validates

ChosenSQL migrations plus ddl-auto=validate.

OverHibernate auto-DDL.

BecauseGenerated columns, HNSW/GIN indexes, partial unique indexes and triggers need hand-written SQL, and validation catches mapping drift.

ADR-03

pgvector inside PostgreSQL

ChosenVectors and keyword indexes in the same table as the chunk metadata.

OverA separate vector store, or Spring AI's PgVectorStore table.

BecauseOne transaction per ingestion, joins to document status, semantic search in HQL and keyword search in plain SQL against the same rows.

ADR-04

Reciprocal Rank Fusion for hybrid ranking

ChosenRRF, k = 60, equal weights.

OverWeighted score blending.

BecauseCosine similarity and ts_rank_cd sit on different scales; RRF needs no calibration and is easy to explain and test.

ADR-05

Stateless JWT with CSRF disabled

ChosenHS256 bearer tokens, 60-minute TTL, no refresh token.

OverServer sessions with cookies.

BecauseThe API is consumed by an SPA and curl; no cookie authentication means no CSRF vector. Short TTL limits token theft.

ADR-06

Stub LLM by default, local embeddings always

ChosenA deterministic StubChatModel and ONNX MiniLM; real providers by profile.

OverRequiring an API key.

BecauseReviewers can run it offline for free, and evaluation is repeatable.

ADR-07

No public sign-up

ChosenSeeded demo users and supervisor-only provisioning that always creates EMPLOYEE.

OverA registration page.

BecauseBank staff accounts are provisioned by the bank, and self-registration would let someone pick their own role.

ADR-08

404 for other users' requests

ChosenNon-owners get Not Found.

Over403 Forbidden.

BecauseIt avoids confirming that a request ID exists, and nothing is lost for legitimate users.

ADR-09

Execute right after approval, idempotently

ChosenSynchronous simulated execution after the decision commits, guarded by a row lock, a status check, a unique key and @Version.

OverAn async job queue.

BecauseThe action is simulated and fast. Four independent guards make duplicate execution impossible, and a retry endpoint shows idempotency.

ADR-10

Segregation of duties

ChosenA supervisor cannot decide on a request they submitted.

OverAllowing it, since the brief doesn't forbid it.

BecauseIt is standard banking control and closes the obvious bypass.

ADR-11

Typed JSONB payloads

ChosenA sealed RequestPayload hierarchy stored as JSONB.

OverA table per category, or an EAV design.

BecauseCategories differ in shape. Records plus Bean Validation keep it typed in Java, and adding a category needs no migration.

ADR-12

A history table instead of Envers

Chosenrequest_history rows with action, actor, status change, field diff, reason and run ID, plus an audit_event per change.

OverHibernate Envers revisions, alone or alongside the history table.

BecauseEvery change already goes through the service layer, which records the diff in the shape the UI shows. Envers would store the same facts a second time in _aud tables and add a revision listener, for no extra capability here.

ADR-13

Frontend first, contract-driven

ChosenThe full React app on MSW before any backend work.

OverBuilding the backend first.

BecauseThe user wanted to see the product first, and it fixes the API contract early.

ADR-14

Business-logic unit tests only

ChosenJUnit 5 + Mockito on services, policies, the state machine and ranking.

OverTestcontainers, MockMvc and frontend tests.

BecauseUser decision. Security rules live in plain policy classes so unit tests still cover them, and the evaluation suite exercises the live stack.

Assumptions & risks

Assumptions

  • All documents, customers and accounts are synthetic, and no real bank system is called
  • One branch-agnostic tenant: branch_code is informational and supervisors see every branch
  • English-only corpus and questions (Arabic is listed as a bonus)
  • Corpus of 18 documents, about 70 pages: 10 Markdown, 8 PDF, including one v1/v2 pair and one injection document
  • Single backend instance, so a database row lock is enough (no distributed lock)
  • Timestamps are stored in UTC and displayed in the viewer's locale
  • AI cost figures are estimates from a configured price table, not provider invoices
  • Demo passwords are documented and only valid in the demo profile

Risks and limits

  • The stub model shows the plumbing; answer quality depends on the real provider
  • MiniLM is English-centric and short-context; long tables in PDFs may chunk poorly
  • The injection detector is pattern-based, so evidence isolation and the citation guard are the real defence
  • No login rate limiting or account lockout in scope
  • No refresh tokens: sessions end after 60 minutes
  • Business-logic-only tests leave HTTP and persistence wiring to the evaluation run and manual checks
  • The default stub model is extractive: it quotes the best-matching sentences rather than writing a summary, so set an OpenAI or Anthropic key for natural answers
